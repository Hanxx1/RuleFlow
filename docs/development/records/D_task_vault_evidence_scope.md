# RF-038/039 独立 Task × Vault × Evidence：D 侧范围说明

2026-11-25 · D 提交团队评审的工作稿。代码核对基线为主线 `efa9dd5`。下文的首版行为按本轮产品决定整理；接口、DDL、迁移编号及公共实现分工待负责人和 B 结合 C/D 对照结果确认。

## 首版用户路径与责任

用户从独立任务选择本账户已有的 Vault 文件，关联后可在任务内查看、下载、解绑。同一原件可以用于多个任务。解绑或删除任务甲后，任务乙的合法引用和原件字节须保留。B 核资料选择与管理入口；D 核任务侧关联、读取、权限和删除影响。关联已有文件只需建立关系，无需再次上传。Vault 记录文件使用关系；Evidence 记录支持任务结论的原句及来源。仅挂文件不能自动生成有依据的结论。

| 操作 | 当前代码与缺口 | 接手工作 |
|---|---|---|
| 选择已有文件 | Vault 列表已按 owner 查询。移动端 VaultView 以 Case 加载可选步骤，未选 Case 时禁用任务选择。 | B 核任务内选文件与库内管理两个入口；D 提供独立任务身份和已关联项读取需求。 |
| 关联、解绑 | vault_task_links 的复合主键已可表达同文件、多任务。validate_vault_links 要求每个任务所属 Case 同时在 case_ids 中。现有 PATCH 读取旧集合，再删除并重建该文件的所有 Case/Task 关系。 | D 建议复用关系表，逐次校验文件与任务的 owner。独立任务允许无 Case；旧 Case 任务保留原校验。B/D 评审单条关系写入，或能检测过期修改的集合更新。重试、并发及写入失败都须保护旁支关系。 |
| 编辑资料 | VaultView.openEdit 仅读取首个 Case 和首个 Task，save 回传最多各一个。按现有代码，即便只改名，也可能覆盖其余关联。 | B 回核所有管理入口；D 提供同文件关联两任务的夹具，联测改名后两个任务仍可读。 |
| 查看、下载 | 列表支持 task_id，先校验任务 owner，再按 owner 和关联过滤；原件下载按 item_id 校验 Vault owner。账户库读取和任务内读取有不同上下文。 | D 核任务内入口必须验证目标关系。同账户文件在解绑后仍可从本人资料库打开；不能凭旧任务关系继续列出或作为该任务的材料读取。跨账户不得泄露文件或依据正文。 |
| 删除任务 | 现有 Vault 条目 DELETE 会删除存储原件及全部关联。vault_task_links 对 tasks 的外键未声明删除级联。 | D 在任务删除流程内清理本任务关系并验证事务回滚；任务解绑和删除均不能调用 Vault 条目删除。B 保持两个操作在界面上可辨。 |

## Task 与 Evidence 如何读取

旧任务创建依赖 Case；旧 Case 通过资源接口按 evidence_ids 回查依据。D 拟补独立任务的创建、按任务读取和作用域校验，并回归旧 Case 资源读取与状态更新。每条依据先核任务访问权，再核 Evidence 的 owner 和归属。同一原件可供甲乙使用，但各自任务的依据 ID 独立；乙伪造甲的 ID 时显示“依据待核对”，隐藏正文。逐条展示已有 ID、原句、来源、定位和可核验版本，正式 Document 行沿用原引用。用户填写允许没有文档行；缺原件、仅余历史摘录、引用无效、暂时无法核验分别提示。详细读取条件沿用 [D 的已合入评审](D_task_evidence_read_review.md)。

## C/D 改表对照与待裁决事项

| 对象 | D 拟议范围 | 与 C 的交点 |
|---|---|---|
| tasks、evidence | 当前两表 case_id 均必填。提议允许独立 Task 的 case_id 为空；Evidence 可属一个 Case 或一个独立 Task，二者恰一。保留旧 ID、旧 Case 与任务的依据 ID 列表。 | C 的 RF-015 候选基础引用 Case Evidence。C 拟新增的映射若引用 evidence，任何共享表重建都需在同一升级副本上验证映射与外键。 |
| evidence_lines、Document | 保留旧依据、原文档和原行映射，独立任务重用原件时按其自身作用域建依据。 | C 的候选来源映射及跨 Case 共享补充附件单列评审。case_attachment_documents 的关系键调整与 Vault 的任务文件关系分别核对。 |
| vault_items、vault_task_links、vault_case_links | 初步判断多任务挂载可复用现有表；重点是写入校验、关系更新和任务删除。若需重建 tasks，须保留现有关系并检查外键。 | B 核入口及写入语义；C/D 对照附件归属和解绑后的引用保护。 |

**建议提交评审的写入顺序。** 若采用上述归属方案，独立任务和依据在一个事务中先建 Task，再建其 Evidence，最后写回任务引用的 Evidence ID；任一步失败整体回滚。升级演练先做旧库快照，按原 ID 复制旧 Case 行及关系，恢复索引和约束，逐条对照直接外键及 JSON 引用并执行完整性检查；失败回到升级前状态。正式顺序需在包含 C 新映射的副本上验证后定稿。

**需要回复的事项。** B 确认多关联编辑如何保全及任务内下载所需上下文；C 确认拟创建的映射外键、共享附件切片及与共享表重建的先后依赖；D 提供约束草案、失败回滚及旧库对照结果。负责人和 B 据此确认公共接口、权限协议、迁移实施者、编号与合入顺序。确定结果归入既有 [公共决策表](D_public_interface_questions.md)。[C 的 RF-015 契约](https://github.com/Hanxx1/RuleFlow/blob/efa9dd5/docs/development/records/C_RF002_contract.md)

## 实现后的联合验收

以下为待执行用例。用两个合成账户、同账户两个独立任务、一个旧 Case 任务、一个共享文件及各自的 Evidence 建立可重复对照。

| 操作 | 通过条件 |
|---|---|
| 甲、乙分别选中同一已有文件，再重复关联 | 两个任务各列一条，下载摘要与原件一致，Vault 只有一份原件。 |
| 解绑甲；另用相同起点删除甲 | 甲的关系消失，乙和原有 Case 的关系保留，仍可下载相同字节。 |
| B 侧改名；两端同时编辑关联；中途注入失败 | 改名保留全部关系；并发更新保全独立改动或报告冲突；失败不留下半组关系。 |
| 换账户尝试关联、列举、下载、解绑；同账户乙引用甲的 Evidence | 请求不能泄露目标内容或改变归属；同账户错挂依据也无法读出甲的原句。 |
| 混合展示有效依据、历史摘录、手填依据、失效引用 | 逐条按读取评审展示；保留有效项，权限未核实的正文隐藏。 |
| 在同一升级副本上回放旧库、C 映射和故障回滚 | 按原 ID 核 owner、Case、任务状态、每条材料所属任务、原文行、日程关联和文件摘要；校验外键及完整性。旧任务从 done 回退、总数不变但转挂他任务，两类反例均须检出。 |

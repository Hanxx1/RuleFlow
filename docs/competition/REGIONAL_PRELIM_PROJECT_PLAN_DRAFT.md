## 1 项目概述

### 1.1 项目背景

校园申请事务通常同时包含通知正文、条件、附件、材料、截止时间和办理步骤。学生在不同应用中取得信息后，仍需自行判断适用条件、查找个人资料、反复填写表格，并把办理要求转成实际行动。仅保存通知或获得一段 AI 摘要，未必能够帮助用户完成申请。

知事 RuleFlow 以手机端校园事务为主要场景，目标用户是需要处理奖助评选、活动报名等事务的在校学生。拟重点验证三个问题：信息能否可靠转为待确认事项；已确认资料能否在核对、材料准备和填表间正确复用；办理任务能否结合课程安排执行，并随用户反馈调整。

以上是产品问题假设，不能代替已经完成的用户研究。后续由 A 组织真实观察、访谈和试用，记录用户原有办理过程、重复输入、遗漏/返工及对 AI 的理解。**待补：实际场景来源、访谈日期与人数、去标识发现及反例。**不使用未经调查的覆盖率、节时比例或用户规模。`[A 核对]`

### 1.2 项目内容

项目拟提供一条连续流程：

> 导入校园通知及附件 → AI 提出候选事项 → 用户确认创建或关联 → 资格条件核对 → 材料匹配与缺项检查 → 按需智能填写申请表 → 办理清单 → 手动或智能安排日程 → Android 提醒 → 进度反馈与调整。

以一项真实校园申请作为首个验证场景，具体通知、申请类别及模板版本由 RF-004 核实。奖学金申请可以作为候选，但尚未取得原件前不认定其格式一定为 DOCX，也不将每项事务都强制经过填表。独立智能填表、个人资料与经历、材料库、个人知识库、办理清单、日程和课表入口均保留。

本阶段聚焦 Android 手机。不开发电脑端和复杂跨设备同步，不把自动登录学校系统、后台操作其他应用或自动提交申请作为本阶段承诺。跨应用体验主要通过 Android 系统分享接收外部信息，继续在知事中办理，并按需把确认后的文件交给其他应用。

### 1.3 创新点

#### 1.3.1 技术创新点

拟将有来源的 AI 理解、确定性规则核对、授权资料复用、格式适配及受约束排程组合为可追踪的事务流程：AI 负责提出结构化理解和文本建议，规则及业务服务负责校验、状态变更和执行；关键变更由用户确认。该组合需要通过跨模块集成和真实数据验证其价值。

已有 Rule AST、三值逻辑、DAG 和启发式排程是可复用技术基础，不将这些常见技术本身声称为首创算法。多方案搜索、约束评分、草案局部重算属于后续实施目标，尚无性能或优越性结论。多格式填表采用共通业务与格式适配两层，以复用已确认信息并控制各格式的写入边界。`[B/C/D 核对]`

#### 1.3.2 功能创新点

项目重点是让同一份信息在真实办理中连续使用。例如，通知中的材料要求关联到已有文件；确认后的个人信息参与条件核对和表格填写；清单任务进入日程；用户反馈办理进度后，系统提出有原因说明的调整，而不是重复要求用户从头输入。

与一次问答的交互目标相比，本项目计划保留来源、确认状态、办理记录和可编辑产物。实际差异需在对照任务中展示，不能据此声称所有聊天产品均无类似能力。初赛应演示已联通的链条，并明确剩余计划。`[A 统稿，B/C/D 提供运行依据]`

#### 1.3.3 其他创新点

交互设计拟突出“可理解、可修改、可拒绝”：资格缺信息时保留 UNKNOWN；字段歧义时显示来源与候选；日程冲突时说明约束；拒绝建议不改变正式安排。Android 分享、文件交付和提醒应嵌入用户已有应用使用习惯，减少来回搬运信息。

创新价值以资料复用正确性、操作衔接、用户理解及实际任务完成来验证。当前没有完成竞品实测或用户对照实验，差异化结论待补；不使用“国内首创”“准确率领先”等无依据表述。`[A 核对]`

## 2 技术方案

### 2.1 总体架构

现有工程采用 Vue 3、TypeScript、Pinia 构建移动界面，通过 Capacitor 6 接入 Android；服务端采用 FastAPI，使用 SQLite 及文件存储。客户端已有本机 IndexedDB Workspace，服务端已有按账户隔离的业务与文件资源。模型配置由服务端管理，普通用户不需要提供 API Key。

| 层次 | 现有工程与复用位置 | 后续增量与责任 |
|---|---|---|
| 手机交互与本机资料 | `mobile/src` 页面/状态；`clientWorkspace.ts`；分享桥 `core/native/share.ts` | B 资料/填表，C 导入/办理，D 日程/课表；A 协调公共交互 |
| Android 平台 | `mobile/android` 中 ShareReceiverActivity、PendingImports、FileProvider | 复用分享输入；B 文件输出，D 提醒，A 环境/集成验收；插件是否新增先验证 |
| API 与业务服务 | `server/app/main.py`、`schemas.py`、`api/planning.py` 及 services | 各模块按契约增量实现，A/B 牵头公共一致性，不先大规模重构 |
| AI 与确定性计算 | `ai.py` Provider、规则引擎、`schedule.py`、`schedule_drafts.py` | C 起首个公共 AI 扩展并与 B 共审，B 实现字段/理由消费；D 负责排程增强 |
| 存储与格式 | SQLite、Document/Vault、原件解析、客户端 Workspace | 按来源/授权/版本关联；增加填表草稿与格式适配；不提前合并所有物理存储 |

核心数据流拟分为七步，当前实现程度见 1.2：

1. 外部应用经系统分享交入信息，或用户在 App 内导入；接收本身不授权上传。
2. 用户确认解析/模型处理范围，保留原件和可定位引用；模型输出候选而非直接执行命令。
3. 用户确认候选创建或关联 Case；来源、Evidence、材料与 Task 保持可追踪关系。
4. 读取用途范围内的已确认资料/经历；确定性规则核对条件，未知信息提示核实。
5. 按需选择真实申请表，形成字段草稿，经用户编辑和确认后由格式适配器另存导出。
6. 清单 Task 结合课程及已安排日程形成手动安排或智能草案；再次确认后写入正式日程。
7. 用户完成、改期或补充事务信息后，解释受影响项和建议；计划中的局部重算仍须确认，不能静默覆盖正式安排。

数据关系、接口错误、版本和授权由 RF-002/003/012 先确认。表中路径是现有模块定位，不意味着未来 Schema 已落地。`[A 核对整体；B/C/D 核对边界]`

### 2.2 功能详述

#### 通知理解与事项办理

复用现有文本、链接和附件处理，逐步补齐导入失败恢复、附件类别识别和多候选确认。当前分析会先创建一个 Case，新方案需调整候选阶段、原文引用、确认幂等及旧数据兼容，不能只增加前端多选框。

资格核对沿用白名单 AST 和 TRUE/FALSE/UNKNOWN；无证据、字段缺失或不支持的条件保持待核对。材料匹配除文件名外，需要考虑类别、有效期、适用事务及用户确认。对已有材料与经历的引用采用统一接口，C 不另建个人档案。办理任务继续保留证据与通知 Review 门禁。`[C 核对]`

#### 个人资料、经历与智能填表

B 负责完整业务。先补齐有效资料读取和手工确认经历，再接入 AI 经历提取等增强。资料存储、退出清理、备份恢复、第三方处理及草稿留存以 RF-012 决策为准；不默认全量上云。

智能填表拟分两层：通用业务层处理字段语义、资料/经历匹配、AI 理由建议、缺失/歧义提示、草稿版本、人工修改及确认；格式适配层处理结构解析、位置定位、受控写入和导出。用户已编辑的值不能被后台建议直接覆盖，历史确认草稿不能因资料更新无提示改变。

DOCX 与 XLSX 写入均为长期既定目标。先核实真实原始模板格式/版本，完成一种模板从解析、匹配、确认到可编辑导出的闭环，再扩展另一种。DOCX 验证表格、段落、合并及分页；XLSX 验证工作表、单元格、合并、公式、前导零和打印结构。原件保留，审核/签字区不自动填造；超长内容不能静默截断。XLS 评估兼容/转换，PDF 区分表单、普通与扫描件，不承诺统一直接编辑。`[B 核对]`

#### 日程、课表与执行反馈

D 复用现有 Task、课程占用和排程草案，先明确独立 Task、来源与状态关系，再完善课表导入和约束一致性。借鉴课程表应用的导入交互需要核实实际文件/文本格式；不默认能登录或抓取任意教务系统。

计划提供单项/多项排程选择、候选比较、人工编辑、片段固定与局部重算。用户可以手动安排；取消建议不修改正式日程。任务、分段日程和提醒需统一完成/跳过/取消/删除语义；一个片段完成不自动代表整个事务完成。提醒随已确认日程变化调度/取消，权限被拒时仍应保存日程并说明限制。`[D 核对]`

#### Android 系统级体验及错误恢复

已有 ShareReceiver 通过 ContentResolver 读取内容 URI，进入私有待处理队列；前端再引导导入和确认。需分别验证冷/热启动、多文件、连续分享、取消及失败恢复，避免处理一次后误清其他未处理内容。

文件输出和本地提醒尚缺完整实现/设备证据。先用一个合成文件和一条合成日程验证，再分别接 B、D 的正式业务。现有 FileProvider 和浏览器下载链接不能单独证明文件已在 Android 正确保存。网络或模型不可用时清晰显示失败及重试选择，Offline Demo 与新输入处理相互区分，禁止预置结果冒充在线成功。`[A/B/C/D 按分工核对]`

## 3 项目计划

### 3.1 可行性分析

#### 3.1.1 技术可行性分析

项目不是从零开始。现有重构工程已经分开移动端、服务端、共享协议和测试，有可复用的通知/规则/任务/资料/文件基础；已有验收记录支持继续进行增量开发。较高风险集中在多候选确认的数据兼容、真实模板写回、独立 Task 状态、排程约束一致性及 Android 交付。先确认契约与做小实验，可以减少三人并行开发后返工。

| 风险 | 先做什么 | 未通过时的安排 |
|---|---|---|
| 模板格式或保真超出能力 | RF-004 核原件，005 人工字段最小写回、复读及编辑 | 记录确切不支持点；选择另一个有代表性且确实可用的真实场景，不能自制表冒充原模板 |
| 关系/版本契约冲突 | RF-002/003/012 一份共同关系与状态表 | 暂缓依赖迁移；继续无依赖模板/样例/界面准备 |
| Android 无法构建或输出/提醒受限 | RF-006 基线，007 两个合成样例 | 分清工具链与业务问题；列待解决缺口，不用 Web 运行替代手机验收 |
| 模型波动与费用不明 | 标注样本、共享 Provider、调用预算/去重及实际错误记录 | 保持确定性流程和人工核对；如实限制在线展示，不返回 Demo 冒充 |
| 计划量超出实际投入 | 按首批成果、阻塞和三条链最小切片滚动选卡 | 延后未开始的覆盖范围/增强，稳定主责、保留长期目标 |

验证围绕同一个真实事务和同一发布版本，覆盖通知与附件、条件/材料、模板填写/编辑、清单/日程及反馈。技术测试与用户观察并行推进，不等最后一周才接设备或收集反馈。

| 验证内容 | 记录方法（尚无结果时留空） | 责任 |
|---|---|---|
| 理解/资格/材料正确性 | 人工标注字段/条件与来源；记录正确、错误、未知及无证据断言；给出样本范围和分母 | C，B 核资料适用性 |
| 填写与保真 | 按可判定字段统计正确匹配/错误/人工确认；检查未填区、结构、长文和可编辑输出；区分建议准确与用户纠正后正确 | B |
| 排程正确性 | 合成边界与真实课表逐例验证冲突、依赖、截止、重复提交、旧版本和任务状态；比较候选须用同一约束 | D |
| Android 与闭环 | 设备/系统、冷热分享、权限、断网、保存/打开/提醒取消、跨模块操作轨迹 | A 组织，B/C/D 修模块问题 |
| 用户价值 | 观察原方法与作品方法的相同任务；记录完成/中断、耗时、重复输入、返工、理解与可修正性；说明样本及学习效应 | A 组织，全员提供材料 |
| 性能/流量/成本 | 区分上传、解析、模型、写入、下载的耗时/错误与字节；记录请求次数/usage；费用仅在实际账单或可核对计价基础上计算 | 模块负责人实测，A 汇总 |

不预填人数、准确率或改善百分比。用户验证需取得必要同意、使用受控/去标识数据；演示合成资料必须注明，历史通知复演注明年份和性质，不能说成当前正式申报。`[A/B/C/D 核对验证范围]`

#### 3.1.2 资源可行性分析

团队采用三人主力开发、一人统筹与集成验收；允许各业务负责人用 Codex 跨前后端实现，但必须人工理解、审查和验证。A、B 牵头公共一致性，C、D 可在业务任务中实现必要公共增量，不等待 A/B 写完全部基础设施。

可用 Android 设备、服务器/域名/模型 API 预算、真实模板及实际视频制作人员尚待落实，相关任务按依赖推进。按实际成果和阻塞调整尚未开始的任务数；不以固定工时、Codex 额度或 token 登记作为开工前置，也不把六周计划作为成员工时承诺。B 的完整填表链与公共审查均占容量，通过减少阶段覆盖控制风险，不将其核心中途拆给 C/D。

官方通知对原创、参赛历史及赛期核心开发有要求。团队已确认本项目没有参加过其他比赛，本次参赛作品的核心开发、关键组件和主要开发工作在本届比赛期间完成，不存在已知的重复参赛或核心开发不符合赛期要求的问题，不再设置重复资格核查任务。真实来源见 [PROVENANCE](../development/PROVENANCE.md)，保留正常代码、许可与版本追溯。

#### 3.1.3 市场可行性分析

当前面向校园事务的使用需求验证，不预设商业化收入或市场占有率。学校和事务之间的格式、规则及流程差异较大，首期以一个真实代表场景证明可用性，再评估模板复用和扩展成本。需求访谈、现有工具对照及持续使用意愿尚待验证，计划书提交版据真实结果补充应用价值和局限。`[A 核对]`

## 4 总结与展望

### 4.1 可行性分析

本节沿用官方模板标题，对第 3.1 节作总结：项目有可复用工程基础，近期可行性取决于真实模板、跨模块契约、Android 和部署验证，不以功能数量代替完成度。优先用一条真实事务证明“理解→确认→行动→反馈”的价值，并保留独立入口。

后续逐步扩大 DOCX/XLSX 模板覆盖、经历适用性、约束搜索与草案局部调整。XLS/PDF 依据样本和技术实验分类型推进。跨设备学习资料和电脑端分工仅列未来研究，不进入当前任务；新增 idea 须比较用户价值、演示性、复用、工作量和回归风险，必要时替换低优先级增强，不能无限叠加。

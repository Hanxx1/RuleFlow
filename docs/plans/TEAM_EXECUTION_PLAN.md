## 1. 执行目标与边界

围绕一个真实校园事务，逐步完成“通知及附件获取→理解候选事项→用户确认创建或关联→资格核对→材料准备→按需填表→清单与时间安排→提醒、反馈及调整”。同时保留独立填表、资料经历、材料库、知识库、清单、日程和课表入口。

三名主力均负责自己业务的前后端、必要平台接入、测试、修复和技术说明。Codex 用于辅助实现，负责人须理解并审查结果。A 对协调和交付质量负责，不代写三个模块，也不接手所有模块测试和修复。

**内部目标为 2026-12-15：整个项目（含新增课程管理）的功能、测试及团队确定的参赛材料达到可直接提交比赛官网的状态。**不是内部演示检查点。具体 DDL 和验收门槛见第 5 节；目标不代表已完成或保证能按期完成。**官方初赛截止仍为 2027-01-15 18:00**，不得把 12-16 以后默认作为完成核心功能或制作正式材料的开发窗口。原 57 项需求保持，长期可选研究与未经验证的格式能力仍按既有边界管理；任何既定核心需求的删减须用户批准。

本阶段不新增电脑端、多端同步、后台自动重排、自动登录学校系统或自动提交申请。DOCX、XLSX 写入均为既定目标，先用一种真实原始模板贯通，另一种按验证和容量继续实现；不能将“能读取文件”写成“已支持填写导出”。

### 2.1 课程管理功能分工与协作

补充日期：2026-11-09｜项目：有绪CampusWeave。本节记录新增课程管理的产品方向、人员职责和最新交付目标；与现有功能并行开发，正式产品边界见开发指导第 11 节，近期 CM 任务及阶段 DDL 见本次更新。**课程管理由 C 提出，因此由 C 主导产品设计、业务开发和整体协调；C 主导不等于由 C 一人完成全部功能。**原有业务主责、RF-001～057 归属及 A、B 共同牵头公共技术的安排保持不变。

#### 1. 新增功能概述

以下为已确定的产品方向，不表示当前代码已实现；具体 API、数据模型和迁移方案仍待后续评审。

① **课程档案与课程要求**：按不同学期管理课程，每门课有独立详情页，包含总览、课程要求、任务和资料。支持常用字段、自定义字段、编辑及修改历史；一门课程可关联多个上课时间规则。

② **课程任务**：支持老师布置的作业、实验报告、小组项目，以及用户自行创建的学习任务。小组仅记录成员和分工，不建设多人在线协作系统；复用现有 Task，不建立第二套任务系统。

③ **课表与时间安排**：完善日视图和周视图，将课程与上课时段、日程、任务关联，避免重复显示课程或重复计算时间占用。

④ **统一 AI 导入**：统一导入入口与课程详情导入共用处理流程，一次输入可同时涉及多门课程及普通校园事务。AI 生成多项建议，由用户逐项核对和确认；支持冲突核对、疑似重复处理、人工纠错及失败项单独重试。保留证据，不允许 AI 未经确认直接修改正式业务数据。

⑤ **课程资料与知识库**：复用现有知识库，一份资料可关联多门课程，支持按课程查看和检索资料，正确处理资料更新、删除与引用失效。

⑥ **数据存储与备份**：课程档案本机优先保存；知识资料复用现有服务端知识库，大文件按需缓存。支持手动导出、导入备份，恢复前预览并允许选择合并或覆盖；删除课程时，由用户逐项决定关联内容的处理方式。

#### 2. A、B、C、D 新增职责

① **A：统筹与集成。**原有职责不变。协调课程管理与现有功能的开发，组织跨模块接口及数据契约评审，协调公共文件修改和代码合并；组织 Android 真机测试及整体集成验收，将课程管理纳入比赛作品、测试及提交材料。A 不默认承担其他成员的具体业务开发与模块测试。

② **B：课程知识库相关功能。**原有个人资料与智能填表职责不变。负责课程资料与知识库的关联、一份知识资料关联多门课程、按课程查看与检索；负责相关资料更新、删除、权限和引用失效处理，备份恢复后的知识资料关联有效性检查，以及这些能力的接口、测试和联调。**本次只确定新增课程功能涉及的知识库工作由 B 负责，不将原有全部知识库任务转交 B；第 3 节 RF-050 仍由 C 主责。**两者涉及同一知识库能力或公共文件时，按下述协作约定共同评审和协调实现，避免重复建设。

③ **C：课程管理主导。**原有通知理解与事项办理职责不变。因课程管理 idea 由 C 提出，由 C 主导整体业务设计、功能串联和跨模块协调；负责课程档案、课程要求、自定义字段，课程规则编辑、来源及历史记录，课程列表、详情等主要业务页面。负责统一导入的 AI 识别与多目标建议、用户确认与归属修改、冲突处理与重复提示、混合导入的执行状态协调及失败恢复交互，并衔接原有 Case 办理流程；负责自己模块的开发、测试及技术说明。C 不独自承担全部公共代码、知识库或排程开发，不得另建与现有系统不兼容的 Task、Evidence、知识库或 AI 服务。

④ **D：课表、任务与日程。**原有个人日程、课表和智能排程职责不变。负责新课程档案与现有课表关联、同一课程多条上课时间规则、完整日/周视图、课程任务与现有 Task 的关联；保证课程时间与日程、排程占用一致，处理课程任务截止时间变化对日程的影响；负责备份恢复后的课程时间规则有效性检查，以及自己模块的开发、测试和联调。D 不承担课程规则管理、知识库实现或统一导入 AI 识别的主责；此处不转移原 RF-040 中由 C 负责的清单页面工作。

#### 3. 跨成员协作与责任边界

① C 是课程管理整体主导者，负责组织课程业务与其他模块的衔接；与 B 共同确定课程和知识资料的关联方式，知识库相关新增实现由 B 负责。

② C 与 D 共同确定课程、课表、Task 和日程的关联方式，任务及日程相关新增实现由 D 负责；C 的课程页面及办理流程消费同一套能力。

⑤ 备份恢复及课程删除等跨模块流程由 C 串联课程业务，B 检查知识资料关联，D 检查课程时间规则及任务、日程关联，A 协调公共边界与整体验收；具体契约和迁移方式留待评审。各成员负责自己模块的测试、问题修复和联调证据，不把所有测试交给 A。

## 6. Android 实施边界

源码基线 `c589990` 中，Capacitor 6 的实际原生工程位于 `mobile/android`。已有 `ShareReceiverActivity` 通过 ContentResolver 读取内容 URI、`PendingImportStore` 保留私有队列、`PendingImportsPlugin` 和 `core/native/share.ts` 传递并清理已处理快照。Manifest 有 FileProvider，主 Activity 注册了 PendingImports。`mobile/package.json` 的现有原生依赖包含 Preferences，未见完整的文件输出或本地通知插件；现有 Blob 下载链接不能证明 Android 保存成功。

因此：分享接收优先复用；文件输出/提醒已有插件是否足够，结论是**当前声明的依赖不足以证明完整能力，必须做 007 验证**。本计划不安装插件，不提前指定未经验证的包版本。确需新增时，比较兼容 Capacitor 6 的成熟插件与现有 FileProvider 上的最小桥，记录必要性、权限和错误语义后选择；无需新原生框架。

# 知事 RuleFlow｜现有工程工作量评估与开发任务拆解

日期：2026-11-03。源码基线：`c589990`，检查开始时工作区干净。本文是工作量评估，不是成员工时承诺或六周全量交付承诺；当前已确定的人员主责与首批安排以 [团队执行计划](TEAM_EXECUTION_PLAN.md) 和 [首批任务](SPRINT_01_TASKS.md) 为准。

## 1. 先读这部分：分工决策结论

**剩余工作量属于较大的增量开发，不能按“已有项目再补几个页面”估算，也不需要从零重做。**通知导入、证据、规则、任务、材料文件、知识检索和基本排程已经有真实实现。主要新增集中在多候选事项的数据关系、独立清单、结构化经历、多格式填表，以及可编辑、可局部重算的排程草案。

三个业务包适合作为三名主力的主要工作方向，但**不适合各给一人、完全独立开发到最后再合并**：

- “个人资料与智能填表”新增链路最多，工作量最大；不能再把所有公共 AI、文件和部署工作都交给这个包。
- “个人日程与智能排程”现有基础较多，但约束一致性、草案固定与重算、真机提醒的调试风险高，不能按页面数量估量。
- “通知理解与事项办理”复用最多，却承担最关键的来源、证据和事项关系改动；这些改动会阻塞其他包，必须优先评审。

最需要警惕的是：**旧数据兼容迁移、真实模板保真写入、本机资料的保存与授权边界、排程预览和提交不一致、Android 文件与提醒、模型调用重试和预算。**它们都不是 Codex 一次生成代码就能算完成的任务。

建议立即开始小范围准备和技术验证，暂不同时铺开三条大功能链。先确定接口样例、真实模板、原生能力和数据边界，用第一批小任务测出团队实际调试效率，再决定阶段范围。当前按已确定分工推进，设备和服务器条件、模板样本及数据语义决策按任务依赖落实；固定投入时间或 Codex 额度登记不作为开工前置。

本文拆出 **57 个任务条目**，包含契约准备、验证、编码、联调和交付证据；这是持续开发任务池，不是六周必做清单。DOCX 和 XLSX 写入都是确定目标；分批实现不等于取消其中一种。XLS 和不同 PDF 的交付方式仍需样本验证，本文只为其安排可执行的验证任务，不虚构已确定的写入方案。

## 2. 依据、检查范围与估算口径

依据为 [工程约束](../../AGENTS.md)、[项目入口](../../README.md)、[文档导航](../README.md)、[最新开发指导](../development/NEXT_PHASE_DEVELOPMENT_GUIDE.md)，并参考 API、架构、前端能力说明和重构验收报告。历史人员分工、旧六周计划没有用于决定本报告的任务归属。

本次定向阅读了 `server/app` 的路由、Schema、迁移、AI、规则、文件与排程服务，`mobile/src` 的实际路由、页面、状态与原生桥，`mobile/android` 的接收器、队列、Manifest、设备测试，以及 `shared` 和相关测试、部署配置。不是逐行安全审计，也没有以文档代替源码判断。

**状态口径：**“已有”仅表示源码存在；“部分基础”表示可复用但不能满足完整需求；“新增”表示在本次相关源码及路由检查中没有发现完整实现；“待验证”表示缺少当前环境、真实样本或设备的验收证据。推荐的新实体、接口和迁移都不是当前已经存在的能力。

重构报告记录了当时 Windows 下后端 151、前端 74 项测试及 Web 构建等结果，可以作为基线参考；本次没有重新运行，也不把历史数量当作当前 HEAD 的通过证明。该报告的 Android 结论止于 Capacitor sync，缺 SDK 时未构建新 APK；Docker、真实在线模型和设备验收不在该报告的已通过范围。本次没有探测成员机器、服务器或账号额度，不能断言现在仍然缺 SDK，也不能断言已经补齐。

### 2.1 工作量与难度分开看

| 级别 | 工作量含义 | 本报告使用方式 |
|---|---|---|
| S | 局部、边界明确、影响小 | 样本确认或有限兼容验证；仍要有结果证据 |
| M | 一条受控流程或少量相关模块 | 包含编码、定向测试、错误处理和必要接口联调 |
| L | 多模块、状态较多或需要复杂联调 | 可作为功能任务，但执行时按卡片中的自然边界分成多个小 PR |
| XL | 整条大功能链 | 三个完整业务包及“完整多格式填表”均属这一层，不能直接作为一次 Codex 任务；以下已拆为 S/M/L |

难度“高”指正确性或技术未知较大，不等于代码最多；例如格式验证可能代码很少、调试很难。工作量不按代码行数或模型生成耗时估计。不提供看似精确的人时总和：样本版式和运行环境等仍影响工作量，以首批成果、测试验收及技术阻塞调整后续任务，不要求分项工时统计。每张开发卡均包含本模块测试和必要联调，最后的集成任务只计算跨模块验证，不替各开发者补单测。

任务池分布为 S 级 2 项、M 级 39 项、L 级 16 项。这些级别是相对大小，不能直接按数量平均分人；公共依赖、设备等待和不同样本的风险也不能通过简单加分消除。

### 5.2 可以安全并行的组合

- 第一组：真实模板/写入实验、Android 基线、接口/旧数据关系梳理。不同文件和环境，结果互为后续依据。
- 契约固定后：通知候选 UI、填表格式适配器、排程候选纯函数。各自独立文件；公共类型、路由和迁移由维护人按顺序合并。
- 手工经历 CRUD 与通知候选存储可并行；两者分别改本机 Workspace 和服务端表，但必须使用已约定的引用类型。
- 课表 UI、原生文件桥、知识更新可并行；Workspace、Manifest、迁移仍各有一个合并入口。

不能安全并行的典型组合：两人改 Evidence 迁移；两人分别重写 ai.py；同时大改 PlanSchedule 和 solver/draft 提交协议；一人在公共类型中改字段、另一人让 Codex“自动修复全仓类型”。这些改动即使 Git 自动合并成功，也可能发生业务冲突。

## 6. 三个业务包是否合理

| 候选包 | 判断与自然边界 | 工作量/风险 | 建议调整 |
|---|---|---|---|
| 通知理解与事项办理 | 合理。包含导入→候选→用户确认→资格/材料→同一办理清单，前后端应保持一起 | 大；关系改动最关键，旧逻辑复用多但回归面广 | 经历档案归包 2，经历资格“是否被本通知认可”由本包消费；统一 Provider/迁移维护不是本包无限兜底 |
| 个人资料与智能填表 | 合理。资料确认、模板、草稿、匹配/理由与写回同链路，拆成纯前端/AI 容易反复交接 | **最大**；通用业务、两个格式写入和新页面大多新增 | 不再附加全部 AI/部署/Android；格式适配可作为有契约的独立小任务由其他开发者协作，业务闭环仍保持一名主维护 |
| 个人日程与智能排程 | 合理。课表占用、求解、草案和执行反馈连续 | 大；算法、时间/状态、设备提醒风险高 | Task 是公共基础；材料清单交互仍在包 1；本地提醒业务映射本包负责，原生桥由公共平台维护协作 |

建议采用 **“三个纵向业务包＋小型公共任务队列”**，不另设第四个由一人包办的技术平台。公共维护人可以兼任业务开发，但其公共工作必须占用该人的容量；不能给他完整业务包后再假定公共工作免费完成。具体成员暂不指定。

包 2 若长期明显过载，优先把 033/034 的受控格式适配任务或 049 原生文件桥分给有空余且完成走读的人，保持同一 TemplateMapping/确认快照契约。不要把经历存储和填表资料适用性拆成互不沟通的两套服务，也不必为平衡人数大规模重构。

适合单人跨前后端完成：手工经历 CRUD、一个明确材料状态操作、课表预览修正、受控知识更新、候选选择页的闭环。适合由一人实现但必须交叉评审/联合验收：迁移、Case/Evidence 确认事务、统一 Provider、授权与删除、草案提交、Android 桥和格式导出。一个人可以是主维护，不能同时被视为唯一设计者、开发者和验收人。

“3 人主要编码＋1 人统筹/交互/质量/材料”可行的条件是：统筹工作有具体交付物，三名开发者各自承担模块测试和技术文档，并且公共原生/部署工作有人留出容量。第四位仍可承担交互样例、失败路径验收、用户试用、跨模块问题定位、定向前端 PR 和材料证据整理；这些都是实质贡献，不按提交数量衡量。本文没有指定 A/B/C/D 最终职责，也未沿用旧分工中的视频责任人。

## 7. 公共技术层维护边界

每项公共能力明确一名技术维护责任人和一个相关业务复核人；可以兼任，但不要求同一人负责全部公共层。维护人保障一致性，不替各包完成所有接口设计。

| 公共领域 | 集中维护的内容 | 各业务包自己负责 |
|---|---|---|
| Schema/迁移/证据 | migrations 编号与顺序、bootstrap 兼容、owner、Case/Task/Evidence/Material 关联、API 兼容 | 提出本业务字段、样例、旧数据影响和测试；共同评审，不等队长独自设计 |
| AI Provider | 请求/重试、能力版本、预算/幂等、日志和安全错误 | 各能力输入最小化、Schema、提示词、证据/业务校验和语义评测 |
| 本机资料与文件引用 | Workspace 版本、有效资料读取、授权快照、FileRef、删除/历史边界 | 经历/表单/材料用途规则和 UI；不另造平行 store 或文件目录 |
| Task/日程契约 | Task 来源/状态、Schedule 版本、草案提交和提醒事件 | 办理清单交互、排程偏好/方案、课程导入，各自实现且联验 |
| 公共前端 | core/http、router、types/product、通用错误/状态组件、必要导航 | 各 features/view、页面状态测试；不在一个 PR 全局格式化 |
| Android 与运行环境 | Manifest/原生桥/依赖、SDK 构建、文件 URI、环境注入和发布 | 分享后办理、文件业务状态、日程变化与提醒映射，不由原生维护者猜业务 |

不新增重复 AI 服务、第二套材料清单、第二套用户资料库；不以并行开发为由迁移全部文件存储或先拆光 main.py。确有必要的新服务可在现有 services/features 下增量落地，避免大范围目录改造。

## 8. 最低必要协作规则

1. **一项任务一个短期分支/独立工作区。**可用 `feat/RF-xxx-主题`、`fix/RF-xxx-主题`；不是三个人在同一目录切分支，更不能共用正在写入的 SQLite、上传目录和运行端口。各工作区按 README 配环境，生成目录不提交。
2. **卡片先定范围再让 Codex 开工。**输入包含本卡 ID、指导对应章节、可复用函数、允许改动文件、禁止扩大事项、接口样例、兼容要求和验收命令。发现需要动公共文件先协调，不让模型自行“顺手统一全仓”。
3. **公共文件按时间段排他修改。**高热点为 `main.py`、`schemas.py`、`migrations.py`、`bootstrap.py`、`ai.py`、`clientWorkspace.ts`、`types/product.ts`、`router.ts`、`PlanView/PlanSchedule.vue`、Manifest、package/lockfile。排他只针对这些文件/契约，不把整个业务包锁死。
4. **契约由提供方提出、消费方确认。**明确路径/方法、nullable、枚举、owner、revision、consent、幂等键、错误码；现有部分错误为字符串，新接口统一结构而客户端保持旧兼容。Mock 与真实接口用同一组样例。
5. **迁移集中排序。**不各自占用相同编号、不改写已存在迁移历史。合并前在临时旧库验证新旧数据、索引/约束、重复执行和失败恢复；不得在真实数据上试错。
6. **小 PR 按可理解结果合并。**L 卡分自然子步骤，接口/迁移先合，再服务、UI 和联调；不提交长期半成品破坏主分支。PR 写问题、变化、验证、未验项和回退方式。不能通过重写 OpenAPI 指纹掩盖未评审变更。
7. **开发者负责模块质量，跨包人员负责复核边界。**修改 Rule/DAG/parser/share 跑相关测试，UI 状态补测试；合并批次按 CI 要求检查。整体验收者查闭环和失败恢复，不接手所有人的单测/文档。
8. **实际资源受限时继续推进独立工作。**模型 API 不可用时，源码定位、契约、合成数据、Mock Provider、确定性匹配与写入可离线推进；一次 Codex 任务控制范围，生成后先读 diff 再测试。仅在资源不足确实影响任务时记录阻塞，不统计 Codex 额度/token 或人工与 AI 分项耗时。

建议一个轻量任务板即可：待契约→可开发→开发中→待评审/联调→已验收。每个开发者同时一个主要任务，遇公共依赖阻塞转去已确认的独立小任务。接口变化当天同步样例；集成遇严重问题先修复已合并切片，暂停叠加新依赖。无需复杂企业流程或长期多人分支。
